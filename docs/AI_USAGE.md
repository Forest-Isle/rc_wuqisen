# AI 使用说明

本项目按作业规则使用 AI 辅助需求分析、设计和实现，但最终工程边界与验收结论由开发者确认。

## AI 提供的帮助

- 从作业 PDF 中提取提交物、系统边界、可靠性和演进问题，建立逐条验收表。
- 比较 Go/PostgreSQL、NestJS/BullMQ、Spring/Quartz 与消息队列方案。
- 枚举崩溃窗口、重复投递、幂等竞争、租约恢复、长期失败和优雅停机等故障场景。
- 补充 SSRF、DNS rebinding、重定向、敏感 Header、请求大小等安全检查。
- 辅助起草迁移、状态机、HTTP API、Worker、测试和容器配置。
- 在实现后运行格式化、静态检查、竞态测试、真实 PostgreSQL 集成测试和本地端到端 smoke，并根据失败反馈修改代码；Compose 镜像构建也被纳入检查，但仍受外部镜像仓库可用性影响。

## 未采纳的 AI 建议

- **Redis + BullMQ**：会增加第二套持久化和运维面，且带来幂等记录与队列的一致性问题。
- **Kafka 或 RabbitMQ**：当前没有吞吐指标证明需要 Broker；第一版引入会把问题变成数据库/Broker 双写。
- **Spring Boot + Quartz**：成熟但对这个 MVP 过重，框架代码会削弱核心可靠性设计的可见度。
- **“Exactly once” 投递**：HTTP 副作用无法由发送方单独保证恰好一次；诚实采用至少一次并传递稳定通知 ID。
- **供应商适配器、模板系统**：调用方已经知道 URL/Header/Body，提前抽象会增加耦合。
- **自动死信重放与管理后台**：凭据错误或永久 4xx 未修复时自动重放没有价值，也需要额外审计和权限模型。
- **第一版多地域和跨区域复制**：没有 RPO/RTO 依据，属于提前承担分布式一致性成本。

## 人工确认的关键决策

- 选择 Go + PostgreSQL，以一个事实源完成持久化、幂等和调度。
- 选择至少一次投递，明确崩溃窗口，并通过 `X-Notification-ID` 把去重能力交给供应商。
- 采用数据库队列、短事务领取和租约恢复，不在网络调用期间持有事务。
- 将 JSON HTTP 通知作为 MVP 边界，不实现二进制、表单、业务工作流或动态模板。
- 将私网目标拦截、白名单、禁重定向和日志脱敏纳入第一版，而不是把安全留到以后。
- 用真实 PostgreSQL 和本地供应商进程验证关键语义，不以 mock 单独证明数据库并发行为。

AI 生成的内容不是验收依据；仓库中的测试结果、运行时 smoke 和人工 diff 审查才是最终依据。
